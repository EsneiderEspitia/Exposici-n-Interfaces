Interface Segregation

¿Qué es el Principio de Segregación de Interfaces?

La "I" de los principios SOLID formulados por Robert C. Martin ("Uncle Bob")
Definición Formal
"Los clientes no deberían estar obligados a depender de interfaces que no utilizan."
— Robert C. Martin ("Uncle Bob"), Agile Software Development (2002)

📜 Contrato Orientado

En Java y POO, una interfaz representa un contrato formal.

Si el contrato impone métodos que la clase no sabe o no debe cumplir, se genera acoplamiento innecesario y artificial.

✂️ Role Interfaces

Es preferible tener múltiples interfaces pequeñas y específicas (orientadas a roles) que una sola interfaz pesada y sobrecargada (Fat Interface).

Alta cohesión funcional y bajo acoplamiento en cada abstracción.

☕ Enfoque en Java

Java soporta herencia múltiple de interfaces:

implements Imprimible, Escaneable, Fax

Permite ensamblar con precisión quirúrgica las capacidades reales de cada entidad.

💡 Clave para la exposición: Enfatizar que una interfaz debe diseñarse pensando en quien la CONSUME (el cliente), no solo en quien la implementa.

❌ El Problema: "Fat Interfaces" (Interfaces Grasas)

Interfaces monolíticas que acumulan demasiadas responsabilidades no relacionadas
Antipatrón

⚠️ Consecuencias del Mal Diseño

  • Acoplamiento Forzado: Las clases clientes conocen y dependen de operaciones ajenas que jamás van a invocar.
  • Efecto Dominó: Si se modifica la firma o parámetros de un método en la interfaz, todas las clases implementadoras deben actualizarse y recompilarse.
  • Rompimiento del Polimorfismo: Si un cliente llama polimórficamente a un método esperando que funcione y la clase lanza excepción, colapsa la aplicación en producción.

Diagrama Conceptual del Error

<<interface>> DispositivoMultifuncion
├── + imprimir(doc)
├── + escanear(doc)
└── + enviarFax(doc, numero)

          │ (implements)              │ (implements forzado)

💥 Consecuencia: ImpresoraEconomica arroja UnsupportedOperationException
⚠️ Advertencia: Forzar a una clase a implementar métodos que físicamente no puede realizar destruye la coherencia del diseño OO.

🔍 Síntomas de Violación del ISP ("Code Smells")

Patrones comunes en código Java que denuncian una interfaz sobrecargada
Detección de Errores

🔴 1. Métodos Vacíos (Dummy)

Implementaciones con llaves vacías o retornos por defecto solo para silenciar al compilador de Java:

@Override
public void escanear(String doc) {
    // Vacío: esta máquina no escanea
}

🔴 2. Excepciones Forzadas

Lanzamiento intencional de excepciones no comprobadas en tiempo de ejecución:

@Override
public void enviarFax(...) {
    throw new UnsupportedOperationException(
        "Hardware no soportado");
}

🔴 3. Comentarios de Alerta

Advertencias textuales en el código pidiendo a otros programadores no invocar el método:

// OJO: No invocar este método aquí
// Esta clase no tiene módem de fax
public void enviarFax(...) { ... }

🔴 4. Efectos Colaterales en Clientes

Clientes que fallan o sufren regresiones por modificaciones en métodos que su módulo nunca utilizó ni necesita.

✅ La Solución: Interfaces de Rol (Role Interfaces)

Descomponer contratos generales en acuerdos específicos, modulares y cohesivos
Diseño Limpio

🎯 Estrategia de Segregación

  • Descomponer: Partir la interfaz gorda en interfaces pequeñas guiadas por capacidades funcionales.
  • Composición por necesidad: Cada clase implementa exactamente los contratos que le corresponden.
  • Dependencia mínima: Quien solo necesita imprimir pide Imprimible; no le importa si el dispositivo sabe o no enviar faxes.

📐 Modelo Segregado

<<interface>>
Imprimible
+ imprimir()
<<interface>>
Escaneable
+ escanear()
<<interface>>
EnviableFax
+ enviarFax()
• ImpresoraEconomica implements Imprimible
• ImpresoraLaserAvanzada implements Imprimible, Escaneable, EnviableFax
• EscanerFotografico implements Escaneable
💡 Cero métodos basura: Ninguna clase implementa métodos vacíos ni lanza excepciones forzadas.

🖨️ Ejemplo 1: Dispositivos de Oficina (Código Java)

src/com/uniajc/isp/ejemplo1_dispositivos/ (violacion vs solucion)
Demostración 1

❌ Violación (Interfaz Gorda)

public interface DispositivoMultifuncion {
    void imprimir(String documento);
    void escanear(String documento);
    void enviarFax(String doc, String num);
}

// Impresora básica forzada:
public class ImpresoraEconomica 
       implements DispositivoMultifuncion {
    public void imprimir(String doc) { ... }

    public void escanear(String doc) {
        throw new UnsupportedOperationException(
            "Hardware no disponible"); ❌
    }
}

✅ Solución con ISP (Segregada)

public interface Imprimible { void imprimir(String doc); }
public interface Escaneable { void escanear(String doc); }
public interface EnviableFax { void enviarFax(String doc, String n); }

// Impresora básica solo implementa lo que hace:
public class ImpresoraEconomica implements Imprimible {
    public void imprimir(String doc) { ... } ✅
}

// Avanzada implementa las 3 por composición:
public class ImpresoraLaserAvanzada 
       implements Imprimible, Escaneable, EnviableFax { ... } ✅
💻 Ejecución en consola: java com.uniajc.isp.ejemplo1_dispositivos.solucion.MainSolucion

🤖 Ejemplo 2: Trabajadores vs Robots (Código Java)

src/com/uniajc/isp/ejemplo2_trabajadores/ (violacion vs solucion)
Demostración 2

❌ Violación: Métodos Absurdos

public interface Trabajador {
    void trabajar();
    void almorzar();
    void tomarDescanso();
    void cobrarSalario(double monto);
}

// El robot NO come ni descansa ni cobra salario:
public class RobotAsistente implements Trabajador {
    public void trabajar() { ... }
    public void almorzar() {
        throw new UnsupportedOperationException(
            "Un robot no tiene necesidades biologicas"); ❌
    }
}

✅ Solución con ISP: Roles

public interface Trabajable  { void trabajar(); }
public interface Alimentable { void almorzar(); }
public interface Descansable { void tomarDescanso(); }
public interface Remunerable { void cobrarSalario(double m); }
public interface Recargable  { void recargarBateria(); }

public class ProgramadorHumano implements Trabajable, 
       Alimentable, Descansable, Remunerable { ... } ✅

public class RobotAutomata implements Trabajable, 
       Recargable { ... } ✅
🎯 Desacoplamiento por cliente: El Gestor solo pide Trabajable, Cafetería solo pide Alimentable, Nómina solo pide Remunerable.

🔗 Relación del ISP con los Demás Principios SOLID

Sinergia del ISP en el diseño orientado a objetos
Arquitectura SOLID

S — Principio de Responsabilidad Única (SRP)

Una interfaz con métodos inconexos (imprimir + escanear + fax) tiene múltiples razones para cambiar. Segregar interfaces garantiza que cada contrato tenga una única razón de existir a nivel de abstracción.

L — Principio de Sustitución de Liskov (LSP)

Cuando una clase lanza UnsupportedOperationException para esquivar un método forzado, rompe LSP: ya no puede sustituir confiablemente al contrato padre. ISP previene este error de raíz.

D — Principio de Inversión de Dependencias (DIP)

DIP nos pide depender de abstracciones y no de clases concretas. ISP asegura que dichas abstracciones sean mínimas y enfocadas, evitando depender de métodos irrelevantes.

🏢 Beneficios en la Industria y Proyectos Reales

Impacto directo en calidad, mantenibilidad y escalabilidad del software
Ventajas Reales

🛠️ Mantenibilidad y Aislamiento

Bajo acoplamiento. Cualquier cambio en una interfaz afecta exclusivamente a los módulos que la usan, previniendo regresiones inesperadas en el resto del sistema.

🧪 Pruebas Unitarias Limpias (Mocks)

Al hacer testing con JUnit o Mockito, no hay que simular decenas de métodos ajenos a la prueba. Los dobles de prueba (stubs/mocks) son compactos y rápidos.

🧩 Reusabilidad Modular

Las interfaces pequeñas actúan como piezas de Lego que se pueden recombinar en nuevas clases a medida que surgen nuevos requerimientos de negocio.

📖 Código Autodocumentado

La cláusula implements Imprimible, Escaneable describe con precisión exacta qué puede y qué no puede hacer una clase sin necesidad de leer su implementación.

✔️ Checklist de Diseño para el Desarrollador

Guía práctica antes de crear o modificar una interfaz en tus proyectos
Buenas Prácticas
☑️ ¿Todas las clases que implementan esta interfaz necesitan y utilizan el 100% de sus métodos?
☑️ ¿Hay alguna clase con métodos vacíos o que lance UnsupportedOperationException?
☑️ ¿Si agrego un nuevo método aquí, obligaré a clases no relacionadas a actualizarse y recompilarse?
☑️ ¿Puedo descomponer este contrato en interfaces más pequeñas y especializadas por rol?
💡 Regla de Oro: "Una interfaz debe ser tan pequeña como sea posible, pero no más pequeña de lo que tenga sentido funcional."

📝 Conclusiones

Síntesis para fijar el aprendizaje del Principio de Segregación de Interfaces
Resumen

1. Especificidad de Rol

El ISP prioriza interfaces compactas y coherentes sobre contratos monolíticos y acumulativos.

2. Eliminación de Contaminación de Código

Evita tener que escribir código de relleno con métodos vacíos o excepciones artificiales en tiempo de ejecución.

3. Sinergia en Java

Se aprovecha al 100% mediante la implementación múltiple de interfaces y favorece la composición sobre la herencia.

4. Pilar Arquitectónico

Facilita pruebas unitarias limpias, mantenibilidad a largo plazo y desacoplamiento estructural entre subsistemas.
